# Phase 27：CLOSの表現と受け入れ案

2026-11-12。tque #319。rack方式と以下のPhase境界はユーザーが承認済み。

## 配置の比較

`zig build bench -- clos-layout` で実行できる。実装は `tests/bench/clos_layout.zig`。
ReleaseFast、Zig 0.17.1、Linux x86_64、Intel Core i7-8700K。各方式を温めた後、
1,000万回の読み取りを測り、逐次実行した5回の中央値を取った。

| 方式 | ns/読み取り（中央値） | 5回の結果 |
|---|---:|---|
| 直接配置 | 1.782 | 1.800, 1.740, 1.815, 1.782, 1.771 |
| rack | 1.832 | 1.765, 1.832, 1.863, 1.914, 1.755 |
| 直接配置・転送後 | 2.683 | 2.585, 2.700, 2.818, 2.683, 2.567 |
| rack・差し替え後 | 1.846 | 1.754, 1.846, 1.873, 1.853, 1.814 |

4スロットを持つ4,096個のオブジェクトを、疑似乱数の添字で読む試作である。
スロット添字は解決済みとし、各回でstampを検査する。直接配置には転送ポインタの検査も含める。
オブジェクトのポインタをコンパイラから隠し、読み取りの消去を防いでいる。
確保・初期化の時間も計測区間には入るが、反復数に対して小さい。
GC、スロット名の検索、クラス再定義そのもの、更新フック、VMの呼び出し費用は測っていない。
確保はpage allocator、配列は連続配置であり、実際のヒープの断片化やキャッシュミスを再現しない。
直接配置は72バイト、rack方式はinstance 24バイト＋rack 56バイト（実ヒープの丸め前）。
この試作だけで処理系全体の速さやメモリ量は判断しない。

推奨は既存設計のrack方式。通常の読み取りで直接配置の差は約3%で、測定のばらつきと重なる。
転送後はrack方式が有利で、同一性を保った再定義を実装しやすい。
実装後に実際のヒープとVM上で再計測し、通常アクセスが明確に遅ければ再検討する。

## P27の受け入れ範囲

- `defclass`、`find-class`、`class-of`、`make-instance` と、クラス名による `typep`。
- CLHSのCPL計算。多重継承・菱形継承と、矛盾する順序のエラー。
- `slot-value` とそのsetf、`slot-boundp`、`slot-exists-p`、`slot-makunbound`。
- スロットの `:initarg`・`:initform`・`:allocation` と `:default-initargs`。
  initformの字句環境、未束縛スロット、共有スロットの継承を確認する。
- conditionと構造体を `class-of`・`find-class` に統合し、既存の型検査・印字・GCとの整合性を保つ。
- 最小サンプルは、クラス定義→作成→スロット読み書き→未束縛化→型判定を含む。

アクセサの総称関数化はP28、利用者が定義する初期化フックとクラス再定義はP29との境界を決める。
P27で先行実装する場合も、単なる同名関数の上書きで総称関数の意味を代用しない。
`with-slots` の展開には `symbol-macrolet` が必要だが、現在は未実装でP30の予定になっているため、
P27の受け入れ条件には含めず、前倒しするなら別途範囲を決める。

## 実装

`src/primitives/clos.zig` と `src/lisp/clos.lisp` に実装した。bootのソースにCLOSを連結し、
VMとネイティブの起動で同じ定義を使う。クラスの公開オブジェクトは `ObjKind.class`、
記述は既存のcondition・構造体と互換の位置0（名前）・1（CPL）を持つベクタである。
名前からの検索はシンボルの属性に保存し、公開クラスオブジェクトをキャッシュする。

標準インスタンスとcondition・restartは `ObjKind.instance` と `ObjKind.rack` で表す。
標準インスタンスのラックはstamp・layoutとスロットを直接並べる。
condition・restartのrackは既存アクセサとの互換性のためスロットベクタを別に保持し、
この2種については試作ベンチマークのインライン配置とは異なる。
構造体本体の直接配置は維持し、公開のstructure-classと `class-of` に統合した。
再定義・古いrackの更新はP29で追加する。
未定義の上位クラスの前方参照はtque #534、`(setf find-class)` による登録・解除は #535で追跡する。
組み込み・condition・構造体クラスのディスパッチ用stampはP28の #536で割り当てる。

受け入れ試験は `tests/language/eval/clos.lisp`（GC stress版もあり）。
標準クラス、菱形継承と矛盾、共有スロット、既定の初期化引数、字句環境、未束縛、
クラスオブジェクトを型指定子に使う形、condition・構造体との連携を含む。
末尾のスロットだけから届くリスト・文字列・ベクタを、確保の繰り返しとGCの後も保持する例を含む。

検証では単体試験のDebug・ReleaseSafe・ReleaseFast、言語試験75本と、Windows・Linux・macOSの
クロスビルド5種が通った。最終のインライン配置への変更後は、新しいCLOS試験をVMとネイティブで
個別に照合し、既存のcondition試験をGC stressで再確認した。CLOSのVM（通常・GC stress）、
ネイティブDebug・ReleaseFast（それぞれ通常・GC stress）はすべて一致した。教材比較は前述のとおり未実施。

ネイティブ全体試験の初回は28本成功・13本コンパイル失敗（実行中のソース編集が原因）。
失敗した13本とCLOSの計14本を固定したソースで再実行し、通常・GC stressとも14本すべて成功した。
これにより全41ケースをカバーした。最後に加えた空クラス・`standard-object` の生成はCLOS試験を
再実行して確認した。検証はLinux上で実施し、Windows・macOSはクロスビルドのみである。
Claude Codeに初回レビューと6件の修正に限定した確認を依頼し、6件すべての対応を確認した。
レビュー原文と対応は `clos-phase27-claude-review.ja.md`。修正後の単体試験Debug・言語77本・
影響するネイティブ4ケース（通常・GC stress）が成功した。ガードの追加で見つかったRuntime再利用の
回帰は、最後に同種restartの再初期化を許す修正とP27限定試験で確認した。全ネイティブ42本の再実行はしていない。
`:type` は宣言として受理するが、P27では実行時の型検査には使わない。
